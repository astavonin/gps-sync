## Findings (8 total — consensus of 3 reviewers)

### Critical

None.

### High

- **H1** [safety / testability / contracts] **The write-phase attribution contract names four per-path conclusions that the declared transport has never been shown to supply.** §5 Phase 3 maps every intended path to exactly one of applied / refused-by-the-re-gate / failed / unattributable, and the transport is declared to return "per-path write conclusions and a process status". No measurement anywhere in the project establishes that a batched exiftool write yields a per-`SourceFile` result at that granularity — the only measured write evidence is aggregate throughput, and the harness verified *which files changed* by digesting them afterwards, not by reading conclusions out of the backend. Two consequences follow. A re-gate refusal becomes indistinguishable from a path nothing came back for, so the pessimism rule routes every concurrency refusal to `Failed{WRITE_UNATTRIBUTED}` (exit 1, remedy "manual inspection") instead of `Protected{POSITION_APPEARED}` (exit 0, remedy "re-run") — inverting both the code and the remedy on the design's own concurrency-defence path, which the design expects to fire because it expects Capture One to be open. And the §6 cases that discriminate the four conclusions run against a substituted transport, which can supply any shape by construction, so two of the four conclusions are asserted against the real binary nowhere. This is the one backend behaviour the audit record's truthfulness depends on, and it is the only place the document asserts an exiftool capability without the measurement it demands everywhere else at that boundary.
  Fix direction: establish the per-path attribution capability as measured evidence at the same standard as the re-gate condition and the container gate, *before* the contract is finalised; require the distinction between a condition-refusal and an unreported path to rest on a positive signal rather than on absence; and extend §6's integration list so each conclusion — including a per-file write error inside an otherwise successful batch — is asserted against the real backend.
  Sites: FR17, FR18, NFR1, NFR8, component map (transport and batched-writer rows), re-gate condition, sequence-diagram message, §5 Phase 3 attribution table, §6 mixed-outcome batch, §6 integration list, §7 write-result-attribution row.

- **H2** [safety / correctness] **FR19's containment refusal contradicts the discovery prune it was meant to sit beside, leaves one documented defence unreachable and one §6 case unsatisfiable, and does not cover the default artifact root.** FR19 and rebuild constraint 4 refuse a `--review-dir` that is, contains, or is contained by the media root — at preflight, exit 2. But FR10 requires the review folder be excluded from discovery "wherever it sits"; the discovery invariant specifies the prune "whether it is inside or outside the media root"; Hazard 1 argues the inside case in detail and asserts "three mitigations are all required, because each alone is defeatable", the third being the prune; and §6 requires the Hazard-1 regression "also be run with the review folder deliberately placed inside the scanned tree, where discovery's prune is the only thing preventing the double count". Under FR19 that configuration exits 2 at preflight, so the test cannot be set up through the tool, the prune has no reachable purpose, and the "each alone is defeatable" argument no longer carries the weight it claims. That configuration is also the one the measured evidence used (TEST-REPORT check 9). Separately, both statements of the rule are scoped to `--review-dir` only, so the derived default root is never containment-checked: `--media ~` places it inside the media tree with no refusal, which is the one way the hazard the rule exists to close is still reachable.
  Fix direction: pick one containment contract and propagate it to every site — either keep the refusal and restate the prune as defence-in-depth against an internal inconsistency (as the symlink assertion already is), withdrawing the "three mitigations" framing and rewriting the two §6 cases to what is reachable; or narrow the refusal to the genuinely unsafe cases and keep the prune live. Either way state explicitly whether the containment test applies to the derived default root.
  Sites: FR10, FR19, constraint row, §4 diagram `DISC` node, discovery invariant, Hazard 1, rebuild constraint 4, failure-class table, §6 (three cases), §7 row; TEST-REPORT check 9.
  *Severity split: raised High by the safety reviewer, Medium by the supportability reviewer. Recorded at High — the finding removes a defence the document calls indispensable and makes a data-loss regression unrunnable.*

### Medium

- **M1** [contracts / correctness] **`Protected` declares `position` mandatory, but `POSITION_APPEARED` has no source for one.** For `POSITION_PRESENT` and `ZERO_POSITION` the value comes from the read record. For `POSITION_APPEARED` the tool learns only that the per-file condition declined; the appeared coordinates are never read, and the transport's declared write result shape does not carry them. Three consumers depend on the field: the JSON per-file record, the altitude-availability reading, and issue 003's destination layout, which is promised a position on every `Protected` file. Filling it with the *planned* position would put a position the file does not carry into the audit record — the adjacent error to the one the reconciliation invariant exists to prevent.
  Fix direction: make the field optional on `Protected` and state what absence means for that reason, as the union already does for `instant` and elevation; or declare the refusal as carrying the observed position and widen the transport's declared result shape. Say which, since the choice changes issue 003's stated extension point.
  Sites: Outcome contract, altitude-in-position paragraph, registry row `POSITION_APPEARED`, attribution table, issue-003 extension point, §6 JSON case.

- **M2** [contracts / observability] **The three write-phase terminal outcomes discard the match payload that three declared consumers need, making two §6 cases jointly unsatisfiable.** `Failed{WRITE_ERROR}`, `{WRITE_UNATTRIBUTED}` and `{WRITE_UNSUPPORTED_CONTAINER}` were all matched and carried `via`, `provenance` and `bracket_speed`; the `Failed` variant carries none of them. So the coverage numerator is required to be "broken out by `via`" while four of its six member classes have no `via`; the sensitivity fold's exclusion enumeration omits `Failed`, though an interpolated file that failed its write holds a speed, so the fold's population differs between a dry run and a write run over the same tree; and the JSON is required to carry each file's provenance. §6 asserts both that a `WRITE_UNSUPPORTED_CONTAINER` member raises the numerator and that the numerator is split by `via` — no implementation satisfies both. This is M3's shape recurring on the variants M3 did not cover.
  Fix direction: decide once whether the match payload survives a write-phase refusal — carry it on variants that were matched, or declare an explicit "matched, no provenance retained" bucket in the `via` breakout — and add `Failed` to the fold's exclusion enumeration.
  Sites: Outcome contract, coverage-rate definition, fold-membership rule, reporter bullet, §5 JSON contents, §6 coverage cases, NFR3, §7 coverage-rate-definition row.

- **M3** [supportability / testability] **The `--verbose` argfile lifetime is specified three times with three incompatible readings, and the purpose it exists for requires the one none of them states.** NFR4 says the argfiles are removed when the run ends, unconditionally, inside the enumeration of what a dry run leaves behind. §5 says they are removed when the run ends, then that "under `--verbose` they are retained for the life of the run" — which is not an exception, since that is the default lifetime — justified by making the "reproduce a write by hand" claim true, which requires survival *past* the run. §6 pins the non-distinction: "absent after the run, except under `--verbose` where they persist for the run". The test cannot be written, the flag's documented effect is indistinguishable from its absence, and NFR4's durable-output enumeration is complete or not depending on the reading. The offered fallback — the intent record carries the same information — covers the write argfile on a write run only, not the read argfile and not a dry run, which is the mode a user debugging a classification is most likely to be in.
  Fix direction: pick one lifetime per flag state, make NFR4 agree, and rest the hand-reproduction claim on whichever artifact actually survives.
  Sites: NFR4, CLI table, §5 argfiles paragraph, §6 (two cases).

### Low

- **L1** [supportability / safety] **The review-folder marker's declared fields have no consumer, so two media roots sharing one explicit `--review-dir` silently overwrite each other's review folder and interleave their audit records.** The marker names the media root and the tool version; the precondition is satisfied by the marker's mere presence, so a second media tree pointed at the same `--review-dir` passes the gate and rebuilds over the first tree's `_unprocessed/` on every run. Only tool-created symlinks are destroyed, so this is not data loss — but the default root is derived per media tree expressly so that two trees sharing a basename do not share a root, and the explicit flag reintroduces the condition the default avoids, with the field that would detect it already written and never read. The version field is likewise unconsumed, so it cannot gate a future marker-format change. This sits against the design's own standard that every requested field has a declared consumer.
  Fix direction: give both fields a consumer — a marker naming a different media root is a refusal or a named warning, a marker of an unrecognised version is a refusal — or drop the fields.
  Sites: marker definition, rebuild constraints, default-root derivation, declared-consumer rule, §6 rebuild cases.

- **L2** [correctness / completeness] **"Out-of-range `--max-gap`" is an enumerated exit-2 failure class and a §6 assertion, but no range is defined anywhere.** The CLI contract says only "duration, non-negative", and the duration grammar makes a sign a parse error — so negativity is already covered by a separately asserted class and no upper bound exists in the document. The class is therefore either empty or undefined: a test pinned to an unstated rule, which is the prior L1's shape recurring on a new rule.
  Fix direction: state the admissible range in the flag inventory, or drop the class and the test term and let the sign rule own it. Do the same for `--extend`.
  Sites: CLI contract row, duration grammar, failure-class table, §6 exit-code enumeration.

- **L3** [completeness] **FR12's preflight destination enumeration omits the per-run temporary directory**, which §5's preflight phase and the failure-class table both include and whose unwritability is a declared exit-2 condition.
  Fix direction: add it to FR12's list.
  Sites: FR12, §5 Phase 1, failure-class table, §6.

## Single-Agent Findings

Findings raised by only 1 of the 3 reviewers. Design reviews do not run Step G, so these are included without adversarial reverification — treat them as lower-confidence than the consensus findings above. Four are nonetheless argued into fix scope in the Recommendation.

### High

- **S1** [safety] The review-folder rebuild's precondition is evaluated at preflight but the removal happens near the end of the run, ~20 s later, leaving a time-of-check/time-of-use window on the one write the design identifies as able to destroy data it did not create. Rebuild constraint 3 is a per-entry bounded-removal rule, but the document states all four constraints are "checked at preflight before anything is removed", and the sequence diagram places the rebuild after the write phase. The exclusive-access assumption is stated for the *media tree* only, and `_unprocessed/` is by design the folder a user browses in Capture One — an application that writes sidecar and catalog files into browsed folders. A foreign file created in that window sits inside a mirrored directory the rebuild is licensed to remove, so it is destroyed rather than refused. Relatedly, link creation is specified as "directories created as needed" with no rule for a path component that exists and is not a real directory.

### Medium

- **S2** [safety] `--keep-original` is the one mechanism that puts a file inside the scanned media tree, and nothing excludes the `_original` sibling from discovery or from becoming a write target. That sibling is by construction the pre-write bytes and therefore positionless, so if discovery admits it, it is read, matched and written — destroying the byte-identity §6 asserts for the retained original and defeating the only mechanism that preserves the prior bytes. NFR4 states the no-new-files property for dry runs only. §6 has no case asserting `_original` siblings terminate `Ignored`.
- **S3** [safety / testability] The gate predicate's three measured states are verified only at unit level over synthetic records. The measurement behind them used `-if '$Composite:GPSPosition'`, while the reader invokes `-j -n` with `Warning` and `Error` requested as tags, and the document makes it a standing rule that every exiftool query has its flag interactions verified before its output is trusted. The integration list covers the indeterminate and present directions but not the XMP-only vendor-namespace case nor the partial-block case — and the partial-block case is the one whose correct reading *creates a write target*.
- **S4** [maintainability] The reason-exhaustiveness assertion runs in the direction that cannot catch the omission it exists to catch. §6 enumerates *the registry* and asserts every row has its five renderings; a reason value introduced in the enumeration without a registry row passes every such assertion and surfaces at runtime in the reporter or review-folder writer. The variant-level mechanism is sound by contrast, because §6 enumerates the union's members.
- **S5** [testability] Binary fixture provenance and repository status are undefined for every integration and E2E case but one. §6 requires real RAF/DNG fixtures throughout, plus real Garmin GPX, but the fixture rule says fixtures are copies created in the test's own temporary directory while excluding the reference archive from all but one conditional test — so the copies' source is both implied and excluded, and the reference GPX tree is a `~/Downloads` path with no repository status and no skip condition. All three previously-untested High categories live in suites whose runnability off this machine is unstated.
- **S6** [contracts / performance] NFR1 permits bounded chunking of the argfile and the archive-wide population makes chunking reachable on the user's own data, but the entire write-phase contract is specified in the singular — one intent record, one spawn, one return, one reconciliation. Nothing states whether the intent record is per run or per chunk, whether reconciliation is per chunk or per run, or whether the file-granular interruption property and the "absence of any record means no writer was spawned" guarantee survive a chunk boundary.
- **S7** [safety / observability] The `intent`-phase record's meaning is stated three incompatible ways: that it means a write process was spawned and did not finish; that it also remains on disk after a *completed and fully reported* run whose completion rewrite failed; and that it is both the "floor" of what might have changed and a "superset" that lists every path the batch intended. The consequence lands in the next run's first report line, which will describe a completed run as an interruption of unknown extent.
- **S8** [observability / supportability] The interrupted-run detection story is incomplete in three ways: the surfacing is flag-dependent (a run interrupted under `--review-dir X` leaves its record in `X/runs/`, and a later run without the flag reads the default root and reports nothing); it is specified for the human report only, so under `--json` — where automated detection matters most — it appears in none of the three JSON content enumerations and no §6 case; and it has no registry row, no remedy and no clearing path, so since the tool never deletes a record it recurs on every subsequent run over that tree forever.
- **S9** [extendability / maintainability] The `-geotag` prohibition is stated as a rule and asserted over "every invocation the shipped code can construct", but the component map declares the transport's input as "argfiles and argv lists" — an open argv pass-through, under which the set of constructible invocations is not statically enumerable and the assertion has no well-defined subject. NFR8 declares three operations and three *result* shapes but says nothing about the argument shape, so the closed-operation-set and pass-through readings are both consistent with the document. This matters exactly where the design says it will: issue 002's MOV path.
- **S10** [observability / contracts] Four registry-declared per-file outputs have no carrier field on the Outcome union, and the reporter is barred from the only other source. `Ignored{SYMLINK}` promises the real target's name, `Ignored{DUPLICATE_INODE}` the retained path, `Unmatchable{BRACKET_UNSOUND}` the two offending trackpoints, and `Unmatchable{MAX_GAP_EXCEEDED}` the smallest admitting `--max-gap` — which equals the bracket width, and `miss_s` is defined as a distance to an endpoint, not a width. §6 nonetheless asserts the figure is rendered.
- **S11** [observability] The per-run sensitivity line reports a median where the question is answered by the tail. FR16's own measured anchor shows median speed 0.15 m/s against p90 1.15 and max 1.61 — a 60 s offset displacing the median photo 9 m and the worst 96 m. On a mixed archive (a walk plus a vehicle transfer, the case FR16 cites as the reason to re-measure per run) the line prints a reassuring single-digit figure while a subset of frames is displaced by hundreds of metres. Every §6 sensitivity case uses a constant-speed fixture, where median and maximum coincide by construction.
- **S12** [observability / extendability] The machine-readable record has no declared top-level shape and no version discriminator, although FR14 promises script consumability and two later issues will extend it (002 adds a third `via` value with a new provenance shape; 003 reads a `Protected` file's instant). A consumer cannot be written against "everything the report carries", and has no way to detect which shape it is holding. The audit record shares the serialisation, so the same openness applies to the only artifact that can audit or reverse an in-place write.
- **S13** [correctness] `--extend`'s interaction with the segment guard is unstated for the two non-disjoint-segment cases, and two §6 cases assert an unconditional refusal that holds only at `--extend 0s`. An ambiguous exact hit and an overlap region are both said to be refused wholesale, but every boundary refusal is eligible for a clamp to the nearer endpoint and in both cases the candidate endpoints are zero or seconds apart — so under the `--extend 90m` the design recommends, the same file is either `Unmatchable{SEGMENT_BOUNDARY}` or `via EXTENDED` with `overridden_reason = SEGMENT_BOUNDARY` depending on a flag neither test names, and the coverage rate differs. Not a fabrication, since a clamp takes a real endpoint — a specification and reporting gap.
- **S14** [correctness / supportability] A tracks root that exists and is readable but holds no GPX file has no defined disposition. A single file yielding no timed points is fatal, with the reason given verbatim: "a silently empty track would present as universal `Unmatchable`". The failure-class table covers a tracks root absent, not a directory, or unreadable — not a readable one with zero GPX files (a mistyped path, a directory of `.fit` exports), which produces that exact symptom across every candidate at exit 0.
- **S15** [correctness] §4 prose and the sequence-diagram note state a stronger exit-2 property than the contract defines. The contract is careful — exit 2 aborts before any per-file outcome is *reported* — but two paraphrases claim every exit-2 condition fires before the first per-file outcome *exists*, which is false for the read-reconciliation abort and for the intent-phase internal-consistency failure. §6 uses the correct form but justifies it with a clause covering only the GPX conditions, so an implementer building the test from §4's wording writes M2's unsatisfiable assertion again, now at the paraphrase.
- **S16** [testability] Four declared exit-2 conditions have no exit-code assertion, while §6's enumeration presents itself as total: the read-reconciliation abort, the writer's pre-emission re-check failure, "read argfile not writable", and "write argfile or intent record not writable" — which has no case anywhere and sits exactly on the 2-versus-3 boundary the fourth code was added to resolve, since an unwritable intent record is literally a run-level artifact the run undertook to produce.
- **S17** [testability] §6 states its unit/integration boundary once — integration is "crossing the real filesystem and a real exiftool" — and contradicts it by placement: roughly twelve Unit cases cross the real filesystem and nothing else, including the review-directory digest regressions, the partway rebuild failure and the stdout-closed case. Two assertions are specified at both levels. So the level marker for the data-loss regression on the one write that could destroy user data is undetermined.
- **S18** [testability] NFR8's standing real-binary check on the transport's declared result shapes is not realised for the time-tag fields — the one group carrying a measured flag trap (`-n` disables `-d`, so a real `-j -n` record returns a different format than a synthetic record takes) feeding the stage §5 calls the largest correctness hazard in the tool. The read integration case asserts record count and process count, not field format.
- **S19** [correctness / maintainability] The §4 flow diagram routes only the gate's "provably absent" branch into time resolution, contradicting the contract that the instant is resolved for every candidate whose record was read — the rule §5 states, the union carries as `instant?` on `Protected`, the invariants restate, issue 003 depends on, and §6 tests in both directions. This is the state prior finding S19 was raised about, fixed in prose and stale in the figure.
- **S20** [safety] The `<ele>` value domain is never defined, "invalid" is never defined, and an invalid elevation is not drop-counted. FR22 requires coordinates be present, numeric, finite, in range and not the `(0,0)` sentinel, but mandates only that the design state what an *absent* `<ele>` means. The validation row reads "`ele` absent or invalid → keep the point" with no criterion for invalid, so a finite but absurd value is admitted, interpolated and written as `GPSAltitude`. Unlike every other defect in the table it produces no drop count, so a track whose elevations are all unusable reports nothing and altitude silently vanishes — in a design that argues at length that a hole must be distinguishable from a deliberate skip.
- **S21** [correctness] FR1 states that `Ignored` outcomes are produced "silently", which two of the three `Ignored` reasons now contradict: §5 says a skipped symlink "is counted and reported, not silently dropped", the reporter names each skipped symlink and duplicate inode once per run, and the registry gives both reasons non-empty remedy text while `NOT_A_STILL` has none. FR1 is a definition site that was not revisited when the symlink fix and the inode dedup landed.
- **S22** [safety / supportability] The rebuild marker has no stated write/remove ordering and no migration rule. The marker is itself removable and the precondition refuses a target that exists, is non-empty and carries no marker — so a rebuild interrupted after the marker is removed and before it is rewritten leaves a non-empty unmarked folder that every later run refuses at preflight: a self-inflicted lockout requiring manual cleanup. Separately, constraint 3 refuses "a directory that is not a declared reason bucket" with no rule for a bucket the tool itself created under an earlier declaration, and the registry's bucket names have already been renamed once.

## Recommendation

**CHANGES REQUESTED** — 0 Critical, 2 High, 3 Medium, 3 Low in consensus, plus 41 single-agent findings.

The fix pass did real work and the structural core is sound. Nothing in this review proposes reversing a design decision, and no reviewer found a Critical finding or a bypass of the never-overwrite invariant. What blocks approval is that both Highs, both of the top two Mediums, and eight of the single-agent Mediums sit in the machinery the *last* fix pass created rather than in the design it was fixing — which is the finding that matters most about process, not just content.

**H1 is not a documentation defect and cannot be closed by editing the document.** It is an open empirical question: does exiftool 13.55, invoked as a single batched write, return a per-`SourceFile` result that distinguishes applied from re-gate-refused from errored? Every other claim at that boundary in this design is backed by a measurement — tag-group acceptance, three flag interactions, container write safety down to byte counts, the re-gate condition's exact form. This one is not, and four declared conclusions, the audit record's truthfulness, the concurrency defence's exit code and remedy, and two §6 cases all rest on it. It is measurable in minutes with the existing harness on copied fixtures. **The measurement should be taken before the contract is edited again**, because if the answer is no, the attribution contract needs a different design rather than different wording — and that is a Phase 2 change, not a fix-loop iteration.

Recommended sequence:

1. **Measure the per-path write-result capability** against exiftool 13.55 on copied fixtures, including a batch containing one unwritable file. Record it in `analysis.md` at the same standard as the existing measurements.
2. **Settle the two decision-level items awaiting the user**, both of which the fix passes have been carrying: exit code 3 added to the three-code contract the user settled personally, and `-overwrite_original` retained at the cost of macOS Finder tags, resource forks and creation dates.
3. **Then one fix pass** covering H2, M1–M3, L1–L3, and the four single-agent findings argued into scope below, with H1's contract rewritten against the measured answer.

**Four single-agent findings argued into fix scope** despite lacking corroboration, on the same grounds used in the initial review — each is a path around an invariant the user stated as absolute, or determines whether the safety argument is reproducible:

- **S1** (rebuild TOCTOU) — a bounded-removal rule evaluated ~20 s before the removal it authorises, on the one directory the design expects another application to be writing into.
- **S2** (`_original` sibling in discovery) — if discovery admits it, the backup copy is itself geotagged, destroying the only mechanism that preserves the pre-write bytes. This is a reachable path to losing the thing `--keep-original` exists to keep.
- **S3** (gate verified only against synthetic records) — the gate is the never-overwrite invariant's sole enforcement point, and the one unverified state is the one whose correct reading creates a write target.
- **S5** (fixture provenance) — determines whether every write-safety and interruption assertion can be re-verified anywhere but this machine, which is what makes the safety argument durable rather than anecdotal.

**On loop mechanics:** the user authorised continuing past the skill's 2-cycle consistency cap, and that was the right call for the cap's stated purpose — the consistency blockers converged monotonically (10 → 5 → 1 → 0) and the remaining items were phrases with supplied replacements. But the cap's *rationale* — "more signals a structural issue requiring design changes, not iterative fixes" — now applies for a different reason. Consensus findings fell 16 → 8 and Highs 3 → 2, so the loop is converging; the mechanism of residual non-convergence is that each fix pass writes new specification, and new specification arrives unreviewed. A further iteration of the same loop will close these eight and plausibly open three or four more of the same kind. The measurement in step 1 is the only item that changes that dynamic, because it replaces an assumption with a fact.
