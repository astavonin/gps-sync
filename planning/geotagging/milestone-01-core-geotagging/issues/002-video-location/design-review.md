## Findings (1 Critical, 10 High, 14 Medium, 10 Low)

### Critical

- **C1** [safety] ✓ **measured by a reviewer, then reproduced independently by the coordinator — a video carrying a container position this tool cannot parse reads as *provably absent*, and the write overwrites it.** `Composite:GPSPosition` is a **derived** tag: when exiftool cannot parse a `Keys`/`UserData`/`ItemList` `GPSCoordinates` value into a lat/lon pair it emits **no key at all**, not a key with an unreadable value. So the gate's three-valued structure collapses to two for a container atom and an unreadable position lands in **provably absent**. The design declares the correct behaviour for this state — `AtomUnreadable → Failed{METADATA_INDETERMINATE}` — and reaches it only from read 2, which FR3 runs only for `TelemetryPath` files; the 47 Fujifilm MOV and 19 Android MP4 this issue newly makes writable go down the GPX path and are **never asked**. Reproduction: plant `+42.0721+077.1292+2189.900/`, gate reads `":GPSPosition": "42.0721 77.1292"` → `Protected`; byte-patch the payload to decimal-comma `+42,0721+077,1292+2189,900/` at identical length so the box size is untouched; the atom is still there under a group-qualified request, the container read returns `{"SourceFile":…, ":FileType":"MP4"}` with **no position key**, the shipped `REGATE_CONDITION` fires, `1 image files updated` at exit 0, and the pre-existing atom is **gone**. Three controls isolate the condition and all three are safe: the ISO 6709 **DDMM** and **DMS** forms parse and are `Protected`, a truncated value parses and is `Protected`, and a comma-list value correctly reaches the *indeterminate* branch. The breach condition is exactly: **the atom exists and exiftool can derive no `Composite` value from it.** Reachable from a foreign writer — a decimal-comma locale is the realistic case — or moov corruption, not from any measured archive file, which is also why no declared test catches it: §6's never-overwrite case represents all three groups with parseable values. **Not reachable in the shipped tool**: 001 admits no video and its write allowlist holds no container format, so this hazard arrives with 002's implementation. It breaches the project's one absolute constraint. *Fix: ask the atom question in the **container** read too — three group-qualified tags added to a list this issue already grows by five, inside a 6 ms/file budget NFR3 already states — and route a non-parsing bare instance into the gate's existing indeterminate value whatever `Composite` says. That also makes FR3's own claim true as written for both paths, and changes nothing on a bare run.*

### High

- **H1** [safety/correctness] ✓ **measured by two reviewers independently — the ISO 6709 coordinate emission is specified only as `abs(v):.9f`, and the QuickTime write set has no hemisphere member to carry the sign.** §5's representability-totality table is the only place in 1,215 lines that states how the `Keys:GPSCoordinates` coordinates are formatted, and it folds them into the stills row, where `abs()` is correct because `GPSLatitudeRef`/`GPSLongitudeRef` carry the sign. The QuickTime set is **one assignment with no reference tags** — §5's own words, "the single assignment carries the whole position". Measured: the tag stores and reads back signs verbatim (`-33.8688 -151.2093` → stored and `Composite` both signed), so an implementation following §5 writes a clip shot at 33.87 S, 151.21 W as **33.87 N, 151.21 E** — both components mirrored, up to ~180° of error, exit 0, empty stderr, reported `Geotagged`, permanent because `Composite` reads the wrong value back and the next run reports `Protected`. Invisible to every test as specified: the archive is 41.9–42.8 N / 73.9–78.5 E, every fixture writes `42.0721 77.1292`, and §6's round-trip case never specifies a negative input. **This is the one defect in 002's own new code** — §5 calls the ISO 6709 formatter "new code in this issue" — and it has survived two full review passes with three reviewers each. One reviewer also found §5 and §6 specify two different precisions for it (9 decimal places vs "16 significant digits"), so an implementer following §5 fails §6 as literally written. *Fix: declare the ISO 6709 formatter separately and signed, state its precision once, and scope the `abs()` row to the two EXIF magnitudes. Test one case per quadrant — an `abs()` implementation fails three of four.*
- **H2** [correctness] ✓ **measured — the refusal class is keyed on a suffix the backend does not always emit, so a refused position-bearing member concludes `Geotagged`.** §5 declares class **R** as a parenthesised `ValueConvInv`/`PrintConvInv` suffix and justifies it as "the invariant part of the backend's own diagnostic". Measured in the shipped eight-assignment block with `-n` throughout: `-GPSLatitude=inf` and `=nan` give `Warning: Not a floating point number for GPS:GPSLatitude` — **no suffix**; `-GPSLatitudeRef=XX` gives `Warning: String too long for GPS:GPSLatitudeRef` — **no suffix**; and `-GPSLatitude=notanumber` gives `Argument "notanumber" isn't numeric in abs in GPS:GPSLatitude (ValueConvInv)`, a fourth wording the design does not have. All are class **O** by the declared predicate, so `count(R) = 0` and the partition falls through to **row 11 → `Geotagged`**. The design generalised a one-tag measurement to a family. **§6 actively asserts the defect**: "a bare `Warning:` with no parenthesised suffix is asserted **not** to be a refusal line" — a suite built to that case passes while all three shapes conclude success. *Fix: key class R on **token resolution** — a line is a refusal when it resolves a `<group>:<tag>` token naming a member this block emitted, with the suffix sufficient but not necessary. That answers §5's own objection to "any `Warning:`", since a benign advisory resolves no emitted member. The read-back of emitted members, declined in §7 on cost, is the only instrument that is not a standing race against exiftool's wording set; this pass's measurements are the argument for re-opening it.*
- **H3** [safety] ✓ **measured by two reviewers converging from opposite directions — the hemisphere sub-case the design says "cannot be measured" is measurable, and measuring it falsifies `WRITE_PARTIAL`'s remedy.** The design states at three sites that the hemisphere members "are literals that no input can corrupt, which is why the hemisphere sub-case cannot be measured". One reviewer asked for exactly that measurement; another made it: `-GPSLatitudeRef=XX` is refused, and the file is left carrying `GPSLatitude 42.0721` with **no** `GPSLatitudeRef`, where `Composite:GPSPosition` reads back **`42.0721 77.1292`** — northern. So a southern position becomes its mirror image permanently, and `WRITE_PARTIAL`'s remedy ("a re-run is safe and will attempt the write again, **because the re-gate still finds no position**") is false for this sub-case: the next run reports `Protected` and never retries. By the design's own test for whether a row earns a split — remedy difference — the two sub-cases differ and the row has not applied its own rule. *Fix: state the measured result, split or qualify the remedy, and correct the three "cannot be measured" sites.*
- **H4** [correctness] ✓ **measured — the new elevation condition's totality claim is false for the *derived* value, and the aggregation step has no outcome for an arithmetic failure.** Asserted at seven sites to be total because `inf`/`nan` "are excluded upstream" and "the formatters cannot emit them". The declared domains check finiteness of each **input**; the condition is evaluated on the **derived** elevation, and the derivation manufactures non-finite values from in-domain inputs: shipped interpolation of two finite endpoints gives `inf` at weight 0.5 and `nan` at 0.0, and `statistics.fmean` over finite in-domain samples **raises `OverflowError` inside the pipeline step**, before the condition can run, in a call the design declares pure and total. Polarity trap: `abs(nan) <= CEIL` is False (caught) but `abs(nan) > CEIL` is also False (**not** caught), and then `abs(ele):.4f` emits the literal `nan` — one of the three inputs the backend does refuse, which is a data-reachable route to the split rows the design says have none. §6 tests `CEIL`, `CEIL+1` and `1e300`; none is non-finite. **This is the failure shape of the H1 this pass was fixing, repeated inside its own replacement text.** *Fix: state the condition as finite **and** within the ceiling, with finiteness explicit so the `>` phrasing cannot drop it; declare the aggregation step's outcome for overflow or a non-finite result; and name the mean implementation, since three reasonable choices give three behaviours on the same in-domain input.*
- **H5** [correctness] ✓ **checked against the tree — FR5 declares blank-vs-absent over all four time tags; the ledger implements it for one, and the gap admits a container atom as UTC.** FR5 and §5's dimension (ii) cover `DateTimeOriginal`, `OffsetTimeOriginal`, `CreateDate` and `CreationDate`; the `records` ledger row adds blank-preservation to **`CreationDate` only**, and `records.py` confirms `date_time_original` and `create_date` both still route through the collapsing `_first`. So a QuickTime record with a present-but-blank `DateTimeOriginal`, one parseable `CreateDate`, no `CreationDate` and `MajorBrand ∈ {isom, mp42}` skips rows 1–6 and lands on **row 9 → resolved, atom as UTC, sole witness** — the exact admission §5 says must not be made, and with more force, since `DateTimeOriginal`'s presence is the evidence the table's whole precedence rule rests on. On the 19 dated Android MP4 a resolved instant decides the match, so this is the wrong-position-into-a-file-that-had-none class. Harmless on stills (a blank collapses to absent → row 7 → the same refusal), which is why 001 never had to settle it. §6 enumerates value-validity cases for all four tags but has no blank-`DateTimeOriginal` case — the omission exactly tracks the ledger's. *Fix: one word in the ledger, plus the case.*
- **H6** [supportability/observability] ✓ **checked against the tree — the bare-run rendering delta is under-counted about eightfold, and the one difference that is declared is self-contradictory.** FR1 and §7 promise three classification differences "every one of which only removes entries" plus **one** rendering difference, and §5 argues this must be declared because "a promise a reader can falsify by diffing two JSON records is worse than a promise of three plus one". The document is now in that state one level up. The suppression column does not prevent the Remedies lines — it governs one list comprehension in `report.py`. **The classification promise itself survives intact**: no reviewer found anything that adds a candidate, a write target or an exit term, and the subset direction holds. It is the declaration that does not. *Fix: replace the "one rendering difference" prose with an eight-row renderer census — `report._counts_section`, `_coverage_line`, `_remedy_text_lines`, the altitude line, `_sensitivity_lines`, `runrecord.summary_to_dict`, `build_run_record`'s registry mirror, `audit._document` — each stating whether its output moves on a bare run and why. Resolve §6's "names every member **present**" against §5's "`CENTROID` at 0": those are two different implementations of `_coverage_line` and only one produces the declared difference.*
- **H7** [correctness/observability] ✓ **two reviewers independently, both against `summary.py` — the altitude breakout cannot account for the figure it replaces.** `summary.py:235` defines `altitude_unavailable` over **every** planned/written file whose position carries no elevation, both paths; `gpx.TrackPoint.ele` is `float | None` and `matcher` yields `ele=None` when either bracket endpoint lacks `<ele>`, so a GPX-matched **still** with no track elevation is in that count today, on the shipped path. The new four-member enumeration lives only on `Centroid`, so that still belongs to **no member**; and `ABSOLUTE_ALTITUDE` names files that *do* carry an elevation and are excluded from the figure by its own definition. §6 asserts the breakout's sum **equals** `altitude_unavailable` on a run mixing all four members — unsatisfiable in two independent directions. §7 half-notices, conceding `Interpolated` and `Extended` carry no altitude field, but draws only the provenance conclusion, not the arithmetic one. Operationally this replaces a correct total line with a breakout that cannot reach it — an observability regression on the stills path already run against real photos, bought for an enumeration three of whose members no measured file reaches. *Fix: state the breakout's domain and its relation to the figure, with the GPX-path no-elevation term appearing explicitly, since §7 already concedes it exists and is unattributed.*
- **H8** [correctness] **the coverage check reads the *used* fixes' span, so a legitimate value-domain drop at the head or tail refuses a sound clip under a reason whose statement is false.** `span_s` is defined over used fixes and the ordered pipeline runs the value domain **before** the span, so any sample dropped at the start or end inflates the shortfall by exactly that much. A clip whose first second of samples sit at the `(0,0)` no-fix sentinel — the canonical shape the sentinel rule exists for, a receiver without lock — exceeds the 1.0 s ceiling and is refused `Failed{TELEMETRY_INCONSISTENT}`, whose label says the telemetry "is not internally consistent" and whose remedy says to re-run. Nothing is inconsistent, re-running changes nothing, and the clip has a derivable centroid over its remaining tens of thousands of fixes. At 59.94 Hz the budget is 60 samples; a real lock acquisition is seconds, so every such clip is lost. §6 enumerates each way the check cannot be evaluated and has no case where the value domain shortened the span. Fails safe — a false refusal, not a wrong write — but it is an undeclared interaction between two rules both restated in this revision, it makes a registry row's own statement false on a representable input, and the fix is one sentence. *Fix: compute the coverage span over the **read** sample-time list, which is already required co-indexed; keep `span_s` over used fixes for the provenance if both are wanted.*
- **H9** [testability] **§6's replacement no-weighting case is unsatisfiable — the comparator it must differ from is the same number.** The previous vacuous case was replaced by one asserting the result equals the plain unweighted mean of the sample list and **does not** equal the hold-length-weighted mean, both computed in the case. Under this document's own definition of hold length (each receiver fix held across exactly six frames) those two means are identical, for uniform and non-uniform holds alike: fixes A held 1 frame and B held 3 give a sample list whose plain mean and hold-weighted mean are both 7.5, while the comparator that actually diverges — the mean over **distinct** fixes — gives 5.0. So the case asserts `7.5 != 7.5`. The slot that was meant to fix a vacuous case now holds an impossible one, and the decision it was meant to pin stays unpinned either way. *Fix: name the comparator §5 actually reasons about — the distinct-fix mean — and keep a uniform-hold list beside it asserted to make the two agree, which is the measured property the decision rests on.*
- **H10** [observability] **the run-level diagnostics assert three rendering surfaces, and no run has three.** `orchestrator` creates the audit writer only under `options.write`, and renders JSON **or** the report, never both. So a run has at most two surfaces and a **dry run** — the default, and the mode in which a forgotten `--tracks` is actually discovered — has exactly **one**. §6 asserts of a single dry run that "the human report, the JSON record's run-level object and the audit record each carry the field", which cannot pass, and it contradicts the document's own closing limitation that one run cannot produce both the report and the JSON record. *Fix: restate the property per renderer and split the §6 case into dry-run report, dry-run `--json`, and write-run audit record — saying explicitly that in the default mode the diagnostic has one surface, because that is the mode the operator is in when it fires.*

## Recommendation

**Do not run a fifth fix pass on this document. All three reviewers reached that independently, from different evidence.**

The prior pass's stall diagnosis is both **confirmed and superseded**. Confirmed: the attribution taxonomy drew findings for the fourth consecutive pass. Superseded: the two worst findings this pass are not in the taxonomy at all. C1 is in the container gate's presence predicate, stable since revision 1, which nine reviewer-passes never probed. H1 is in a formatter the document mentions once, in passing, inside a table about something else — and it is **the one piece of new code 002 actually introduces**. Each took one measurement.

One reviewer stated the cost of the loop exactly: *the taxonomy, by the document's own words, "protects nothing, it only describes" — and it has consumed four passes of review attention while the defect in 002's own new code went unexamined.*

The reviewers also split usefully on whether the object improved, and both halves are true. Measured by **where the lines went**, it did: of this pass's +195 lines, roughly 80 bought prevention upstream of the irreversible write — the elevation condition, the telemetry coverage check, the four-tag validity default — against roughly 60 that bought description, where the previous three passes bought almost nothing but description. The stall condition's premise about growth no longer holds. Measured by **defect rate**, it did not: six Highs, four of them in text this pass wrote, and every one found by running something rather than by reading. The specific failure is now visible and is not "the design is wrong" — the pass measured three refusal shapes against **one tag** and generalised to a family that has at least four members across two tags, two of them suffix-free. That is a measurement-coverage failure, and no further reading of the document will find the next one.

**The order of work, on which all three converge:**

1. **Fix C1 and H1 first, as their own small change.** Three group-qualified tags added to the container read plus one routing clause; one formatter declared signed with its precision stated. These are the only two findings in four passes that put an overwrite or a wrong value into an irreplaceable file from a cause outside this tool's own defects, and both are cheap.
2. **Fix the bookkeeping defects as targeted edits** — H4's finiteness clause, H5's one word in the ledger, H8's span basis, and the two §6 impossibilities (H7, H9). None needs a review round.
3. **Land NFR8's tooling before any implementation, and test it.** It is the only change in the document with no declared test, and it decides whether the next round of defects is found by a machine or by a sixth reading.
4. **Build the renderer census** (H6). One table against the shipped tree answers H6, H7, H10 and three Mediums, because all six are the same question asked at six sites.
5. **Carry out the scope split**, now recommended by three consecutive passes and explicitly by two of three reviewers this pass. The attribution taxonomy, the registry's run-level mechanism and the mutation-tooling change are not about video. What stays in 002 — the two-read probe separation, the `meta`-track gate including C1's fix, the time-evidence dispatch, the centroid and its provenance, the `Keys` write including H1's fix, the three-phase seam, the free-space check, the per-operation vocabularies — is sound, well measured, and the best-tested part of the document.
6. **Then implement, and let the next gate be a code review with the mutation gate live.** The project's own record is unambiguous: every High in 001's code was found by mutation and none by reading; every High in 002's design has been found by measurement and none by argument. The §6 cases that pin the backend — signed ISO 6709, an unparseable atom through the gate, a non-finite derived elevation, the refusal wording matrix, the errored-with-no-`Error:` cell — are an afternoon's work against exiftool 13.55 and would have caught C1, H1, H2 and H4 before they were written.

**Status is CHANGES REQUESTED, not REJECTED, and all three reviewers were explicit about why.** A Critical normally means reject. C1 is one localised gap in a presence predicate, its fix uses machinery the design already has and strengthens FR3's own claim, and the core of 002 is sound and materially better than three passes ago. The problem is not the design's structure. It is that the document stopped being the instrument that finds these defects two passes ago.
